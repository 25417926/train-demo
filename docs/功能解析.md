## 0. 阅读结论（TL;DR）

1. **架构完整**：Spring Cloud Alibaba 微服务拆分清晰，网关统一鉴权，会员、车次、余票、订单、支付、退款、改签均有对应模块与接口。
2. **下单主链路是“令牌削峰 + MQ 异步 + 分布式锁串行 + 位图占座”**，思路正确，但可靠性靠“单机锁 + 单条消息”，没有幂等、重投、认领和补偿。
3. **与参考图四项能力对照**：
   - 库存与重复购票控制：**半套**。有令牌、分布式锁、同乘客校验、二进制占座；缺请求幂等、购票资格记录、同事务扣减、唯一约束与 CAS。
   - 异步购票与消息处理：**半套**。有 RocketMQ 异步出票；缺事务消息/Outbox 可靠投递、消费幂等、消息认领、死信处理。
   - 订单关闭与退款处理：**退款有、关闭无**。缺未付款取消、超时关单、释放流水、退款两阶段预留、资格与订单校验。
   - FIFO 候补补位：**未实现**。没有候补申请、排队、补位、补位超时和再排队模型。
4. **结论**：不应在原链路上零散打补丁，应做一次“购票一致性底座”升级：**幂等受理 → 资格占位 → 事务消息（Outbox 审计）→ 异步出票 → 统一释放 → 候补补位**，并保留现有支付/退款/改签接口兼容。

## 1. 项目定位与总体架构

### 1.1 项目定位

面向铁路售票场景的分布式演示系统，覆盖：

- 基础数据：车站、车次、途经站、车厢、座位
- 每日数据：每日车次、每日车厢、每日座位、每日余票
- 交易链路：余票查询、下单、异步出票、支付、退款/退票、改签
- 会员中心：注册/登录、乘客管理、我的车票、我的订单
- 运营后台：基础数据维护、每日数据维护、令牌、订单、支付、退款、改签、定时任务
- 辅助能力：Quartz 每日车次生成、Knife4j 接口文档、Sentinel 限流、Sa-Token 鉴权

### 1.3 请求链路

```text
浏览器(vue-ui:1001 / admin-ui:1002)
        │  satoken
        ▼
gateway:80  ── SaReactorFilter 鉴权 ── 路由 ──► 各微服务
        │                                      │
        │  登录成功后注入 UserId 请求头          ├─ business:8081 /business
        └──────────────────────────────────────┤─ member:8080 /member
                                               └─ auth:81 /auth
```

- 网关鉴权规则（`gateway/.../SaTokenConfig.java`）：
  - 放行 `OPTIONS` 预检；
  - 禁止外部访问 `/member/internal/**`、`/business/internal/**`、`/batch/internal/**`、`/auth/internal/**`；
  - 除 `/auth/sso/**` 外全部要求登录；
  - `/member/**`、`/business/web/**` 允许 `user` 或 `admin`；
  - `/business/**`（除 `web`）仅 `admin`。
- 服务侧通过 `MemberInterceptor` 读取 `UserId` 头并写入 `LoginMemberContext`；**缺少请求头时不阻断**，直接访问服务端口时上下文可能为空。
- `business` 调用会员服务使用 OpenFeign，当前地址写死为 `http://127.0.0.1:8080`，路径统一走 `/member/internal/feign/**`。
- 登录：`AUTH` 按邮箱查询会员，支持验证码登录（会员端可自动注册）与密码登录（AES 可逆加密后比对）；后台登录要求账号具备 `admin` 角色，角色写入 Redis 供网关 `StpInterfaceImpl` 读取。

## 2. 数据模型解析

### 2.1 实体关系总览

```text
station ──┐
train ────┼──► train_station / train_carriage / train_seat
          │
          └──► daily_train ──► daily_train_station / daily_train_carriage
                              daily_train_seat（sell 位图）
                              daily_train_ticket（按 O-D 的余票与票价）

member ──► passenger ──► ticket（会员库）
   │
   └──► confirm_order（业务库，tickets 为 JSON）
              ├──► payment（1 对 1）
              ├──► refund（1 对 1）
              └──► change_record（原订单 / 新订单）

sk_token：按 date + train_code 的令牌余量
undo_log：Seata AT 预留表（当前链路未启用 Seata）
```

### 2.3 座位 `sell` 位图模型

`daily_train_seat.sell` 的长度 = 途经站数 - 1，每一位代表一个站间区间：

```text
4 个站：A ── B ── C ── D
区间：   [A-B] [B-C] [C-D]   → sell = "000"

购买 A→C（站序 1→3）：
  startIndex=1, endIndex=3 → 取 sell 的 [0,2) = "00"
  本次占座掩码 = "11"，补齐为 "110"
  新 sell = "110"  → A-B、B-C 已售，C-D 仍可售

再购买 B→D（站序 2→4）：
  取 [1,3) = "10" → 含 1，判定已售，不可选

再购买 C→D（站序 3→4）：
  取 [2,3) = "0" → 可选，新 sell = "111"
```

对应代码：

- 选座与占座判定：`business/src/main/java/com/guo/business/service/Confirm_OrderService.java` 的 `getSeat`、`calSell`
- 扣减余票区间：`After_Confirm_OrderService.afterDoConfirm` 调 `CUST_Daily_Train_TicketMapper.updateCountBySell`
- 退款回滚：`RefundService.rollbackSell` 按区间生成掩码后按位与取反

### 2.4 订单 `tickets` JSON 结构

`confirm_order.tickets` 存 `List<Confirm_OrderTicketReq>`：

| 字段 | 含义 | 备注 |
|---|---|---|
| `passengerId` | 乘客 ID | 当前被当作 `member_id` 用于重复购买校验，存在语义错误 |
| `passengerType` | 乘客类型 |  |
| `passengerName` | 乘客姓名 |  |
| `passengerIdCard` | 身份证 | **敏感信息明文落 JSON**，需脱敏/加密 |
| `seatTypeCode` | 席别 | `YDZ/EDZ/RW/YW` |
| `seat` | 选座，如 `C1` | 可空，空则自动选座 |

## 3. 核心业务流程解析

### 3.1 登录与鉴权

**会员端（`vue-ui`）**

```text
POST /auth/sso/SendCode/{email}   → 生成验证码并发送邮件，写 Redis
POST /auth/sso/login              → 邮箱 + 验证码/密码
                                  → 会员端验证码登录可自动注册
                                  → StpUtil.login(id)，角色写 Redis
                                  → 返回 saToken
后续请求 Header: satoken=...
```

**后台（`admin-ui`）**

- 登录时 `source=admin`，账号必须已存在且具备 `admin` 角色，否则拒绝。
- 网关按 `/business/**` 仅 `admin` 校验，`/business/web/**` 允许会员访问。

**服务侧上下文**

- 网关 `AddUserId2HeaderFilter` 从 Sa-Token 取登录 ID 写入 `UserId` 头。
- 各服务 `MemberInterceptor` 解析头 → `LoginMemberContext`；**头缺失时放行**。

**主要问题**

- 密码使用 AES 可逆加密而非哈希，泄露后可直接还原。
- 直接访问服务端口可绕过网关鉴权；`MemberInterceptor` 不阻断匿名请求，依赖业务自检。
- 登录链路存在两套入口（`/member/register`、`/member/LoginCode` 与 `/auth/sso/**`），职责重叠。

### 3.2 车次与余票查询

```text
GET /business/web/train/Query-All
GET /business/web/station/Query-All
GET /business/web/ticket/Query-List?date=&trainCode=&start=&end=
```

- 余票来自 `daily_train_ticket`，按日期、车次、出发站、到达站唯一确定。
- 前端 `vue-ui/src/views/HomeView/daily-train-ticket.vue` 负责展示与进入下单。
- 管理端可维护基础车次、每日车次、车厢、座位、余票。

### 3.3 下单与异步出票（核心链路）

**入口**：`POST /business/web/confirm-order/do-storage`

```text
① 网关鉴权 → business
② Before_Confirm_OrderService.BeforeDoConfirm
   a. 从 LoginMemberContext 取 memberId
   b. Sk_TokenService.validToken(date, trainCode, memberId)
      - Redisson 锁：token_lock:{date}-{trainCode}-{memberId}
      - Redis 计数：token_count:{date}-{trainCode}，>0 则 DECR
      - 每减 5 个回写 DB sk_token.count
   c. 落 confirm_order，status=INIT，tickets JSON
   d. 发送 RocketMQ：topic=order_confirm，body={date,trainCode,logId}
   e. 返回 orderId
③ ConfirmOrderConsumer 消费
   → Confirm_OrderService.DoStorage
   a. Redisson 锁：order_lock:{date}-{trainCode}，tryLock(0, 5s)
   b. 循环查 status=INIT 的订单（每批 5 条）
   c. sell(order)：
      - 校验车次、余票、tickets 非空
      - 校验“同乘客同车次是否已买过”
      - 订单置 PENDING
      - reduceTickets：内存校验并递减余票对象
      - getSeat：按席别查车厢/座位，calSell 判断区间可售
      - 若选座数不足 → TICKET_NOT_ENOUGH → 订单 EMPTY
   d. After_Confirm_OrderService.afterDoConfirm（@Transactional）
      - 逐座位 SeatForUpdate
      - updateCountBySell 扣减余票区间
      - Feign 调 member 写 ticket
      - 更新订单 SUCCESS
```

**状态流转**

```text
INIT(I) ──► PENDING(P) ──► SUCCESS(S) ──► PAID(Y) ──► REFUNDED(R)
   │            │              │              │
   │            ├──► EMPTY(E)  │              └──► CHANGED(X)
   │            └──► FAIL(F)   └──► CANCEL(C)
   └── 无超时关闭
```

**关键实现问题**

| 编号 | 问题 | 影响 |
|---|---|---|
| O-1 | `tryLock(0, 5, TimeUnit.SECONDS)` 指定了 leaseTime=5s，**没有看门狗续期**；批处理循环超过 5s 锁会自动释放 | 并发消费者同时处理同一车次订单，可能重复占座/超卖 |
| O-2 | 锁粒度为 `date + trainCode`，整条车次串行 | 吞吐低，热点车次排队严重 |
| O-3 | 重复购买校验条件为 `member_id = passengerId` | 语义错误，且无唯一索引，并发下仍可重复 |
| O-4 | `DoStorage` 无外层事务；`sell` 中途异常时订单可能停在 PENDING，且部分座位已改 | 状态与库存不一致，且无补偿任务 |
| O-5 | `After_Confirm_OrderService` 在 `@Transactional` 内调用 Feign 写车票 | 远程成功、本地回滚时“有票无单”；远程失败、本地回滚时“有单无票” |
| O-6 | 订单 SUCCESS 在座位循环内更新，而非全部座位成功后统一更新 | 多票订单可能提前成功 |
| O-7 | MQ 同步发送，发送结果不检查、无本地消息表 | 发送失败订单永久 INIT；重复发送无幂等 |
| O-8 | 消费端无幂等；消费异常后订单可能停在 PENDING/PENDING 不再被扫描 | 消息重投无效，订单卡死 |
| O-9 | `reduceTickets` 只改内存对象，真正扣减依赖 `updateCountBySell`；两步语义容易误解 | 维护风险 |
| O-10 | 余票更新无 `WHERE ydz >= n` 条件、无版本号/CAS | 依赖外层大锁，一旦锁失效即超卖 |

### 3.4 支付

```text
POST /business/web/payment/pay
  → 校验订单存在、属于当前会员、状态为 SUCCESS
  → 插入 payment（pay_status=SUCCESS，trade_no=DEMO-{id}）
  → 订单状态更新为 PAID
```

- 演示实现，不对接真实支付通道。
- 无 `payment.order_id` 唯一约束，也没有 `UPDATE ... WHERE status='S'` 条件更新，并发重复支付可产生多条支付记录。
- 无金额与票价一致性校验。

### 3.5 退款 / 退票

```text
POST /business/web/refund/apply
  → 校验订单存在、属于当前会员、状态=PAID
  → 查 payment
  → 查 daily_train_ticket（O-D 余票）
  → Feign: /member/internal/feign/ticket/list-by-order
      按 memberId + date + trainCode + start + end 反查车票
  → 逐票：
      rollbackSell：按区间掩码按位与取反，回滚 sell
      SeatForUpdate
      increaseCountBySell：回加余票区间计数
  → Feign 删除会员车票
  → payment 标记 REFUNDED
  → 订单 REFUNDED
  → 插入 refund 记录
```

**问题**

| 编号 | 问题 | 影响 |
|---|---|---|
| R-1 | 车票反查按“会员+日期+车次+区间”，没有 `order_id` | 同一会员同日同车次同区间有多张订单时，可能删错/退错票 |
| R-2 | Feign 删除车票位于 `@Transactional` 内 | 远程已删、本地回滚时车票丢失 |
| R-3 | 退款直接成功并释放，没有“受理中 → 预留 → 成功释放”的两阶段 | 支付通道失败时库存已释放，产生超卖窗口 |
| R-4 | 无释放流水、无幂等键 | 重试/重复请求可能重复加库存 |
| R-5 | 不能校验“释放的资格是否属于当前订单” | 旧订单重试可能释放新订单占用的名额 |
| R-6 | 退款状态只有 SUCCESS/FAIL 之类，无 REFUNDING | 无法表达“已受理未到账” |

### 3.6 改签

```text
POST /business/web/change/apply
  ① 校验原订单 PAID
  ② 插入 change_record（INIT，手续费 5 元）
  ③ 调 RefundService.refund 退原票
  ④ 原订单状态改为 CHANGED
  ⑤ 调 Before_Confirm_OrderService.BeforeDoConfirm 提交新订单
  ⑥ change_record 置 SUCCESS，记录 newOrderId
```

**问题**

- 整个方法 `@Transactional`，但第 ⑤ 步在事务提交前就发送了 MQ；消费者可能读不到新订单，消息丢失。
- 第 ③ 步退款与第 ⑤ 步新单在同一事务内，但退款内部包含 Feign 远程调用，事务边界不可控。
- 新单参数依赖前端传 `dailyTrainTicketId` 等最简字段，前端改签弹窗要求手填车次/站点/余票 ID，体验与正确性都弱。

## 4. 关键机制深挖

### 4.1 秒杀令牌大闸（Sk_Token）

**作用**：在下单入口按 `date + trainCode` 限制进入异步链路的请求量，避免 MQ 与 DB 被瞬时打满。

**实现要点**

- 令牌总量 = 站数 × 座位数（`Sk_TokenService.genDaily`）。
- Redis key：`token_count:{date}-{trainCode}`，TTL 100 分钟。
- 校验时对每个 `memberId` 加 `token_lock:{date}-{trainCode}-{memberId}` 锁，避免同一用户并发抢令牌。
- 每成功获取 5 个令牌，DB `sk_token.count` 减 5。

**问题**

| 编号 | 问题 | 影响 |
|---|---|---|
| T-1 | 先 `DECR` 再判断 `decrement < 0`，已扣减但返回失败，没有补偿 | 令牌少发，吞吐下降 |
| T-2 | 每 5 个才回写 DB，Redis 丢失时 DB 余量与真实不一致 | 令牌超发 |
| T-3 | Redis key 不存在时直接返回 false，没有从 DB 恢复 | 缓存过期后无法购买 |
| T-4 | 令牌锁按用户加，锁粒度细但 Redis 操作多 | 高并发下 Redis 压力大 |
| T-5 | 令牌只控制“进入量”，不控制“库存正确性” | 不能替代库存幂等 |

### 4.2 分布式订单锁

- key：`order_lock:{date}-{trainCode}`
- 目的：同一车次同一时刻只有一个消费者在处理 INIT 订单，避免并发选座。
- 问题：租约 5 秒、无续期、批处理循环可能超时；粒度粗；消费者多实例时形成串行瓶颈。

### 4.3 余票区间扣减算法

`After_Confirm_OrderService.calcInfluenceRange` 根据新 `sell` 计算本次购票影响的区间范围：

```text
sell = "00000"，本次购买站序 2→4（区间 [1,3)）
新 sell = "01110"

向左找最近已售位 → 得到本次可扣减的起始区间
向右找最近已售位 → 得到本次可扣减的结束区间
最终用一条 SQL 扣减多个 O-D 组合的余票
```

`CUST_Daily_Train_TicketMapper.updateCountBySell` 的具体 SQL 需要按 `minStart/maxStart/minEnd/maxEnd` 扣减对应 O-D 行，是本项目最核心也最容易被误解的一段逻辑。

### 4.4 RocketMQ 异步出票

- Topic：`order_confirm`
- ConsumerGroup：`default`
- 消息体：`{date, trainCode, logId}`，不带 orderId 列表
- 消费逻辑：按日期+车次扫描所有 INIT 订单批量处理

**问题**

- 消息不带业务唯一键，消费端只能靠“扫表”，无法精确幂等。
- 消费异常没有重试策略/死信处理/人工补偿入口。
- 发送与落库不在同一事务，没有 Outbox。
- `consumerGroup=default` 与其它潜在消费者共享组名，扩展性差。

### 4.5 事务与远程调用边界

| 位置 | 事务 | 远程调用 | 风险 |
|---|---|---|---|
| `BeforeDoConfirm` | 无显式事务 | 无（发 MQ） | 落库成功、发送失败 → 订单永久 INIT |
| `DoStorage` | 无 | 无 | 中途异常 → PENDING 卡死 |
| `afterDoConfirm` | `@Transactional` | Feign 写会员车票 | 远程与本地不一致 |
| `RefundService.refund` | `@Transactional` | Feign 查/删车票 | 远程已删、本地回滚 |
| `ChangeService.change` | `@Transactional` | Feign + MQ | 事务提交前发消息，消费者读不到新单 |

**原则**：远程调用不应放在数据库事务内；跨服务一致性应通过“本地事务 + 事件表 + 重试 + 幂等”实现。

### 4.6 幂等与防重现状

| 场景 | 现状 | 缺口 |
|---|---|---|
| 下单重复点击 | 仅靠前端按钮状态 + SK 令牌 | 无 `requestId` 幂等键，无唯一约束 |
| 同乘客重复购买 | 查 `confirm_order`，条件把 `passengerId` 当 `memberId` | 语义错误、无唯一索引、并发窗口 |
| MQ 重复消费 | 无 | 无消费幂等 |
| 支付重复提交 | 无 | 无 `order_id` 唯一约束 |
| 退款重复提交 | 有状态判断（REFUNDED） | 并发下仍可能重复；无幂等键 |
| 改签重复提交 | 有状态判断（CHANGED） | 并发窗口；无幂等键 |
| 库存释放重复 | 无 | 无释放流水/幂等键 |

### 4.7 安全与规范现状

**已有**

- 网关统一 Sa-Token 登录与角色校验。
- 内部 Feign 路径在网关层封禁。
- 后台登录校验 `admin` 角色。
- 密码使用 `PwdAESCryUtil` 对称加密（非哈希）。
- 验证码走 Redis，带过期。
- 全局异常处理 `ControllerExceptionHandler`。
- Knife4j 接口文档。

**缺口**

- 服务端口可被直连，绕过网关；服务侧未做强制登录拦截。
- `LoginMemberContext` 在缺少 `UserId` 头时为空，部分接口可能 NPE。
- 身份证、乘客姓名等敏感信息明文存 `confirm_order.tickets`。
- FastJSON 1.2.70 存在已知 CVE。
- 无明显接口版本号、请求签名、防重放。
- 日志中存在中文乱码（`Confirm_OrderService` 部分 `LOG.error`）。
- 部分调试接口仍保留（如 `Daily_Train_SeatController.test`），需确认是否下线。

## 5. 与参考图能力对照（Gap 分析）

### 5.1 能力成熟度总表

| 参考能力 | 现状成熟度 | 判断 |
|---|---|---|
| 库存与重复购票控制 | ★★☆☆☆ | 有令牌/锁/位图，但缺幂等、资格、同事务、唯一约束 |
| 异步购票与消息处理 | ★★☆☆☆ | 有 MQ 异步，但缺 Outbox、重投、认领、消费幂等 |
| 订单关闭与退款处理 | ★★☆☆☆ | 退款可用，但无超时关闭、无释放流水、无两阶段 |
| FIFO 候补补位 | ☆☆☆☆☆ | 完全缺失 |

### 5.2 库存与重复购票控制

**参考目标**：MySQL 行锁、请求幂等、用户场次记录共同控制库存与重复占位；用 `JdbcTemplate` / `TransactionTemplate` 将库存扣减、订单创建、购票资格记录纳入同一事务，失败整体回滚。

**现状**

- 库存扣减依赖 Redisson 车次级大锁 + `daily_train_ticket` 更新。
- 无请求幂等键，无购票资格表，无同事务约束。
- 重复购买校验语义错误且无唯一索引。
- 余票更新没有条件更新/CAS。

**差距**

1. 锁粒度粗、租约短，吞吐与正确性都受影响。
2. 没有“谁占用了这个名额”的资格记录，无法做释放校验与候补转移。
3. 没有幂等键，重复点击/重试会产生多单。
4. 没有唯一约束兜底，应用层校验在并发下失效。

### 5.3 异步购票与消息处理

**参考目标**：购票请求受理后，通过 Redis Stream 消费者组异步分配名额、创建订单；购票申请与 Outbox 事件同事务保存；支持事件重投和消费者中断后的消息认领；结合数据库状态与幂等约束，避免重复建单和扣减库存。

**现状**

- RocketMQ 异步，消息只带日期/车次，消费端扫表。
- 落库与发送不在同一事务，无 Outbox。
- 无消费幂等、无 PENDING 认领、无死信/补偿。
- 锁租约 5 秒，消费中断后订单可能卡死。

**差距**

1. 消息可靠性没有“至少一次 + 幂等消费”的闭环。
2. 没有消费者中断后的消息认领机制。
3. 没有可观测的重试次数、死信、人工重放入口。

### 5.4 订单关闭与退款处理

**参考目标**：取消未付款订单、超时关闭及退款成功时，在同一事务中归还库存、释放购票资格并记录释放流水；退款受理后预留名额，成功后才释放；校验资格对应的订单，避免旧订单重试释放新订单占用的名额。

**现状**

- 退款直接成功并释放库存。
- 无取消订单接口、无超时关闭任务。
- 无释放流水、无资格校验、无退款中状态。
- 车票反查按业务键而非订单键，存在误删风险。

**差距**

1. 库存“只进不出”或“提前出”，没有受控释放。
2. 退款失败时无法回滚库存状态。
3. 旧订单重试可能释放新订单名额。
4. 没有超时关单，未支付订单会永久占用座位。

### 5.5 FIFO 候补补位

**参考目标**：按同票档候补申请的提交顺序分配名额；在同一事务中完成库存扣减、待付款订单创建和购票资格转移；确保候补优先于新购票；验证取消后重新申请新记录排队、补位订单超时及退款后重新购票等场景。

**现状**

- 无候补表、无排队、无补位、无补位超时。

**差距**

- 完整缺失，需要新增数据模型、接口、匹配器、超时任务与前端入口。

|---|---|
| 令牌 / SK Token | 下单前置令牌，用于削峰，不等于库存 |
| O-D | Origin-Destination，出发站-到达站组合 |
| `sell` 位图 | 每个座位在各站间区间的售卖状态 |
| 资格 / 名额 | 某会员某乘客对某 O-D 某席别的占位凭据 |
| 释放 | 取消/超时/退款后归还库存与名额 |
| 补位 | 候补队列中的申请按 FIFO 获得释放出的名额 |
| Outbox | 本地消息表，业务数据与事件同事务落库 |
| 认领（Claim） | 消费者中断后接管未确认消息 |
| 幂等键 | 保证同一业务请求只生效一次的键 |
