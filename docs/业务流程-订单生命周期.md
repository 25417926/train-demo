## 1. 一句话结论

当前真实可走通的链路只有 5 条：

```text
下单受理 → MQ 异步出票 → 支付 → 退款
                        ↘ 改签（= 退原票 + 重新下单）
```

**取消（C）没有实现；支付失败、退款失败、改签失败都没有落库记录；`ticket_status` 和 `ticket.order_id` 在 Java 代码里从未被写入。**

因此：

- `ticket_status` 不能由 `confirm_order.status` 推导，只能由「会员库里是否存在该订单的车票」判定；
- `ticket.order_id` 必须先在代码里补上写入口，否则新出的票仍然是 NULL，回填一次还会再产生新的孤儿票。

## 2. 状态定义

### 2.1 订单状态（ConfirmOrderStatusEnum，9 态）

| 编码 | 含义 | 代码里是否会写入 | 写入位置 |
|---|---|---|---|
| `I` | 初始（已受理） | 是 | 受理时 insert |
| `P` | 处理中（消费者已认领） | 是 | `sell()` 开始前 |
| `S` | 锁座成功、待支付（`ticket_status='N'`） | 是 | `afterDoConfirm()` 锁座完成后 |
| `F` | 失败 | 是 | 消费异常 / 非余票不足异常 |
| `E` | 无票 | 是 | 座位选不够 / 余票不足 |
| `C` | 取消 | **否** | 无任何入口，也无消费者 |
| `Y` | 已支付 | 是 | `PaymentService.pay()` |
| `R` | 已退款 | 是 | `RefundService.refund()` |
| `X` | 已改签 | 是 | `ChangeService.change()`（覆盖刚写入的 `R`） |

> `P → S/E/F` 是消费侧写入；`S → Y` 是支付；`Y → R` 是退款；`Y → R → X` 是改签（同一事务内先退款再改状态）。
> `I → P` 之后如果消费者崩溃，**没有任何补偿会把 `P` 拉回 `I` 或推进到终态**，这就是卡单。

### 2.2 支付状态（PaymentStatusEnum）

`I` 待支付、`S` 已支付、`F` 支付失败、`R` 已退款。
**代码只写 `S`（支付成功时插入）和 `R`（退款时更新），`I` 和 `F` 从未写入。**

### 2.3 退款状态（RefundStatusEnum）

`I` 处理中、`S` 已退款、`F` 失败。
**代码只写 `S`。失败时整笔本地事务回滚，连 `F` 记录也不会留下。**

### 2.4 改签状态（ChangeStatusEnum）

`I` 处理中、`S` 成功、`F` 失败。
代码先插入 `I`，成功改 `S`；失败分支写 `F` 后**重新抛出异常**，由于方法带 `@Transactional`，`F` 记录会随事务一起回滚。所以「失败记录」实际也不存在。

### 2.5 车票出票状态（`confirm_order.ticket_status`）

改造前：DDL 已加列（默认 `N`），Java 代码中没有读写 `ticket_status`，30 行订单全部为 `N`。

改造后（2026-10-22）：锁座完成写 `N`、置 `P` 写 `I`、出票成功写 `S`、出票失败写 `F`、退款成功写 `N`，并与 `ticket.order_id` 一起维护。

## 3. 五条真实流程（逐步：改了哪张表、留了什么记录、发了什么消息）

### 3.1 受理下单

入口：`POST web/confirm-order/do-storage` → `Before_Confirm_OrderService.BeforeDoConfirm()`

| 步骤 | 动作 | 表变更 | 记录/标记 | 消息 |
|---|---|---|---|---|
| 1 | 校验秒杀令牌（Redis `token_count_*`，失败走 DB 兜底） | 无 | 无 | 无 |
| 2 | 生成雪花 ID，插入订单 | `confirm_order` 新增 1 行，`status='I'`，`tickets` 存 JSON | 订单本身即受理记录 | 无 |
| 3 | 发送 MQ | 无 | 无 | topic `order_confirm`，消息体**只有** `date / trainCode / logId`（**不含 orderId**） |

关键事实：消息不带订单号，消费者是按「日期 + 车次」批量捞 `status='I'` 的订单（每次 5 条，循环直到没有），不是精确消费某一个订单。

### 3.2 异步出票（消费者）

入口：`ConfirmOrderConsumer`（`consumerGroup=default`，`topic=order_confirm`）→ `Confirm_OrderService.DoStorage()` → `sell()`

| 步骤 | 动作 | 表变更 | 记录/标记 |
|---|---|---|---|
| 1 | 按 `date + trainCode` 加 Redisson 锁，`tryLock(0,5s)`，抢不到直接 return（消息被确认，不重试） | 无 | 无 |
| 2 | 批量查 `status='I'` 订单 | 无 | 无 |
| 3 | 校验车次/余票/乘客数/同乘客是否已买 | 无 | 无 |
| 4 | 订单置 `P`，防止重复处理 | `confirm_order.status='P'` | 处理中标记 |
| 5 | 内存扣减余票对象（`reduceTickets`，不落库） | 无 | 无 |
| 6 | 选座（`sell` 位串按区间置 1） | 无 | 无 |
| 7 | 逐座位：锁座位并更新 `sell`；余票数 -1；调会员 Feign 写票；订单置 `S` | `daily_train_seat.sell`；`daily_train_ticket` 各席别 -1；`train.ticket` 新增行；`confirm_order.status='S'` | 车票行 = 出票成功记录；**但没有 order_id、没有 ticket_status** |
| 8 | 余票不足 → `E`；其他异常 → `F` | `confirm_order.status='E'/'F'` | 只有状态，`close_reason` 从未写入 |

出票写入会员车票时，`MemberTicketReq` **没有 orderId 字段**，`Ticket` 实体也**没有 orderId 字段**，所以 `train.ticket.order_id` 永远是 NULL。

### 3.3 支付

入口：`POST web/payment/pay` → `PaymentService.pay()`

前置校验：订单存在、属于当前会员、`status='S'`（已是 `Y` 报「重复支付」，其他状态报「状态不允许」）。

| 步骤 | 动作 | 表变更 | 记录/标记 |
|---|---|---|---|
| 1 | 插入支付记录 | `payment` 新增 1 行：`pay_status='S'`、`pay_time=now`、`trade_no='DEMO-'+paymentId`、`amount` 取**请求参数** | ✅ 支付成功记录 |
| 2 | 推进订单 | `confirm_order.status='Y'` | ✅ 订单已支付标记 |
| 3 | 发消息 | 无 | ❌ 没有 `order_pay_topic/queue` 的生产者和消费者 |

失败分支：只有抛异常，**不会写 `payment.pay_status='F'`，也没有失败流水**。

### 3.4 退款（退票）

入口：`POST web/refund/apply` → `RefundService.refund()`

前置校验：订单属于当前会员、不是 `R`、必须是 `Y`、存在支付记录、余票记录存在、会员车票能查到。

| 步骤 | 动作 | 表变更 | 记录/标记 |
|---|---|---|---|
| 1 | 按 `memberId + date + trainCode + start + end` 反查会员车票（**不是按 order_id**） | 读 `train.ticket` | 无 |
| 2 | 逐票回滚座位 `sell`、余票 +1 | `daily_train_seat.sell`、`daily_train_ticket` +1 | 无 |
| 3 | 逐票删除会员车票 | `train.ticket` 物理删除 | 车票消失 |
| 4 | 支付记录置退款 | `payment.pay_status='R'` | ✅ 支付记录被标记退款 |
| 5 | 订单置退款 | `confirm_order.status='R'` | ✅ 订单退款标记 |
| 6 | 插入退款记录 | `refund` 新增 1 行：`refund_status='S'`、`refund_time=now`、`amount=payment.amount`、`reason` | ✅ 退款成功记录 |
| 7 | 发消息 | 无 | ❌ 没有 `order_refund_topic/queue` 生产/消费 |

失败分支：任何一步抛异常 → 本地事务回滚 → **没有退款失败记录**；但第 3 步删除会员车票是跨服务调用，**不会回滚**，可能出现「票已删、退款记录没有」。

### 3.5 改签

入口：`POST web/change/apply` → `ChangeService.change()`

前置校验：原订单存在、不是 `X`、必须是 `Y`。

| 步骤 | 动作 | 表变更 | 记录/标记 |
|---|---|---|---|
| 1 | 插入改签记录 | `change_record` 新增行：`change_type='C'`、`change_status='I'`、`fee=5.00` | 处理中记录 |
| 2 | 调 `RefundService.refund()` 退原票 | 同 3.4：座位/余票/车票/支付/订单 | ✅ 退款记录 `S`、支付 `R`、原订单 `R` |
| 3 | 原订单状态改为 `X`（覆盖 `R`） | `confirm_order.status='X'` | ✅ 已改签标记 |
| 4 | 复用受理流程创建新订单 | 新 `confirm_order` 行 `status='I'`；发 `order_confirm` | 新订单受理记录 |
| 5 | 改签记录置成功 | `change_record.change_status='S'`、`new_order_id` | ✅ 改签成功记录 |

关键事实：**改签记录 `S` 只代表「新订单已受理」，不代表新票已出**。新订单后续可能变成 `F`（见第 4 节真实数据：3 笔改签成功记录里，2 笔新订单最终 `F`）。

失败分支：catch 里写 `change_status='F'` 后 `throw`，`@Transactional` 使整笔回滚 → **F 记录不会持久化**；而第 2/3 步若已完成，已删除的会员车票同样无法回滚。

### 3.6 取消 / 超时关闭

**未实现。**

- `C` 只在枚举和 `queryLineCount` 的 switch 里出现，没有任何写入口；
- 没有取消接口、没有取消消费者、没有超时扫描任务；
- `expire_at`、`close_reason` 列已加，但代码从不写；
- `P` 状态没有补偿，卡住即永久卡住。

## 6. 代码缺口清单（按影响排序）

| 编号 | 现象 | 影响 | 证据 |
|---|---|---|---|
| G1 | `ticket.order_id` 全链路未写入 | 无法按订单精确退票/对账，回填后继续产生孤儿票 | `MemberTicketReq`/`Ticket` 无 orderId 字段；`TicketService.save()` 不设置 |
| G2 | `ticket_status` 全链路未写入 | 无法表达「出票中/已出票/失败」，只能靠 status 猜 | 全仓库 Java 代码无 `ticket_status` 引用 |
| G3 | 取消 `C` 未实现 | 用户无法取消待支付订单，`expire_at/close_reason` 形同虚设 | 无取消接口/消费者/定时任务 |
| G4 | `P` 无超时补偿 | 消费者崩溃即永久卡单；现网已有 2 笔 | `DoStorage()` 只捞 `I`，不扫 `P` |
| G5 | 支付/退款/改签不发 MQ | 下游无法感知，`order_pay/refund/cancel/complete` 队列全部空转 | 仅 `order_confirm` 有生产+消费 |
| G6 | 失败无记录 | 支付失败、退款失败、改签失败均无落库；改签 `F` 还会被事务回滚；`close_reason`/`fail_reason` 未写 | `ChangeService` catch 写 F 后 throw；`PaymentService`/`RefundService` 无失败分支 |
| G7 | 出票失败不释放已扣库存 | `P` 期间已扣的余票/座位不回滚，可能造成少卖 | `sell()` 在第 7 步前抛异常时无补偿；`E` 分支只改状态 |
| G8 | 退款按「会员+日期+车次+区段」反查车票 | 同会员同区段多订单时会误删别人的票 | `RefundService` 调 `memberFeign.listByOrder`，参数无 orderId |
| G9 | 改签 `S` 语义错误 | 新单 `F` 时仍显示改签成功，原票已退、新票没有 | 3 笔 `S` 改签中 2 笔新单为 `F` |
| G10 | `order_outbox`、`purchase_*`、`inventory_*`、`waitlist_*` 未被代码使用 | I03 新表目前只是空壳 | 代码无对应 Mapper/Service |
| G11 | MQ 消息不含 orderId | 消费者按车次批量处理，幂等粒度粗、无法精确重放 | `Confirm_OrderDto` 只有 date/trainCode/logId |
| G12 | 同乘客校验用错字段 | 用 `member_id = passengerId` 判断，实际不生效，可能误判 | `Confirm_OrderService.sell()` 的 `andMemberIdEqualTo(ticket.getPassengerId())` |
| G13 | 支付金额取请求参数 | 服务端不校验票价，存在篡改风险 | `PaymentService.pay()` 直接 `req.getAmount()` |

## 7. `ticket_status` 与 `ticket.order_id` 的正确判定

### 7.1 为什么不能按 status 猜

- `S` 和 `Y` 都可能持票；
- `R`、`X` 的票在退款时已被删除；
- `P`、`F`、`E` 从未出票；
- 改签链路上原单 `X` 无票、新单可能 `F` 也无票。

### 7.2 可验证的判定规则

对存量数据，唯一可靠的依据是「会员库是否存在该 `order_id` 的车票」：

```text
存在车票 → ticket_status = 'S'
不存在车票 → ticket_status = 'N'
```

前提是先把 `train.ticket.order_id` 补全。当前 22 张票中 21 张已绑定，1 张孤儿票可凭「同会员 + 同日期 + 同车次 + 同区段 + 同座位 D1 + 创建时间在订单受理后 73ms」唯一对应到 `Y` 订单 `2064091034354323456`。

## 8. 目标流程（已确认，I03 已落地）

核心顺序：**锁座 → 支付 → 出票**。`S` 表示「锁座成功、待支付」，不是「已出票」。

```text
① 受理（POST web/confirm-order/do-storage）
   → confirm_order 落库 status=I
   → 发 MQ order_confirm（date/trainCode/logId）

② 排队锁座（MQ 消费者 ConfirmOrderConsumer → DoStorage → sell）
   → 车次级 Redisson 锁，按 date+trainCode 捞 I 单
   → 选座，把 sell 位写回 daily_train_seat，余票 updateCountBySell
   → 写 inventory_hold（每个座位一行，status=H，hold_token=HOLD-{orderId}）
   → confirm_order: status=S（锁座成功待支付），ticket_status=N
   → expire_at = 锁座时间 + 15 分钟（支付倒计时起点）
   → 此阶段【不写会员车票】

③ 支付（POST web/payment/pay）
   → 前置：status=S；已支付(Y) 报重复支付
   → payment 写 pay_status=S（失败复用同一行并写 fail_reason）
   → confirm_order: status=Y
   → 事务提交后投递 MQ order_issue（orderId/logId）

④ 出票（MQ 消费者 OrderIssueConsumer → TicketIssueService.issue）
   → 校验 status=Y、ticket_status≠S
   → 按 inventory_hold 的座位写会员车票（带 order_id）
   → 全成功：ticket_status=S（订单仍为 Y）
   → 失败：ticket_status=F，只记录，座位释放留 I04

⑤ 退款（POST web/refund/apply）
   → 前置：status=Y 且 ticket_status=S（未出票返回「车票正在出票」）
   → 回滚 sell / 余票 +1 → 删会员车票 → payment=R → 订单 status=R、ticket_status=N
   → refund 写成功或失败流水（含 fail_reason）

⑥ 改签
   → 原单走退款，再按受理流程提交新单（新单同样锁座→支付→出票）

⑦ 未支付订单（GET web/confirm-order/unpaid-list）
   → 条件：member_id + status=S + ticket_status=N + expire_at > now()
   → 返回 expire_at 与 remainingSeconds，前端据此显示支付倒计时

⑧ 超时取消（I04，未实现）
   → expire_at 到期：status=C、释放 sell、inventory_hold=R、写 inventory_release_record
   → P 卡单补偿、order_issue 投递失败重试同属 I04
```

当前 I03 的已知边界：

| 项 | 状态 |
|---|---|
| 锁座不写票、支付后才出票 | 已落地 |
| `inventory_hold` 占座账本 | 已落地（锁座时写入 H） |
| `expire_at` 支付截止时间 | 已落地（锁座时 +15 分钟） |
| 未支付订单列表 | 已落地 |
| 超时自动取消 / 释放座位 | I04 |
| `order_issue` 投递失败重试 | I04（当前仅记录日志） |
| 锁座阶段 `tryLock(0,5s)` 租期短、无看门狗 | I04 一并整改 |
