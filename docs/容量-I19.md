# I19 容量与故障演练报告

> 采集时间：2026-10-23（本机）
> 对应 Issue：I19（故障演练与压测，依据 `docs/项目计划.md` 8.6 / 8.7 / 10.3 / 10.4）

## 5. 故障演练

### 5.1 kill -9（business）

- 预写订单 `2113511401283784704` 后 `kill -9` business 进程；客户端连接失败快速返回（3.3 万次失败、1163 次成功受理）。
- 重启后同 `Idempotency-Key` 返回同一 `orderId`；新 key 正常受理。
- 校验：`request_id` 前缀 `kill9%` 的订单每个 request_id 恰好 1 条，无重复建单。
- 副作用：kill 窗口内有 2 条 ORDER_CONFIRM 消息重投耗尽进入 `%DLQ%business-order-confirm`，触发 `MQ_DLQ_NOT_EMPTY` CRITICAL 告警（持续 FIRING），需按运维手册人工重放（I20 范围）。

### 5.2 Redis 重启

- `redis-cli shutdown nosave` 停止 Redis，受理快速返回 500（`ACCEPT_FAILED`），DB 无新增订单。
- 手动重启（AOF 恢复 29356 keys），恢复后首个受理请求耗时 17.2s（Redisson/Lettuce 重连），随后 133ms / 22ms 恢复。
- 校验：`redis-idem-0..4` 每个 request_id 各 1 条订单，无重复建单。

### 5.3 Broker 重启

- 停止 Broker 后，受理 115ms 返回 500，DB 无新增订单，`purchase:req` 已回滚。
- 以 `conf/broker-local.conf`（brokerIP1=127.0.0.1）重启后，同 key 重试成功（`orderId=2113515032020127744`），DB 该 request_id 仅 1 条 `I`。
- 演练暴露并修复：`release.lua` 释放幂等标记原先只按 requestId 生成，同键重试会命中上次标记导致资格残留、永久 `DUPLICATE_PURCHASE`；已改为 `ACCEPT-{requestId}-{orderId}`（`PurchaseAcceptService#rollback`）。

### 5.4 MySQL 行锁（座位热点行）

步骤：外部会话 `SELECT ... FOR UPDATE` 锁定候选池头部座位 `1920000000000003377` 约 38s，期间提交一笔受理请求。

结果：

- 受理接口 31ms 返回 `I`（`orderId=2113515937163513856`），受理与出票解耦。
- `information_schema.processlist` 观察到消费者连接处于 `updating`，阻塞在 `update daily_train_seat set sell='1' ...`。
- 锁释放后消费者自动继续：`TICKET_CREATE` 补投、收尾 Lua 成功，订单最终 `S/S`，端到端约 38s。
- 一致性：该订单 1 条 hold、1 个座位 `sell=1`、member 1 张票，无重复出票。

### 5.5 MySQL 死锁

步骤：两个外部会话交叉锁定已售座位 `1920000000000003377` 与 `2064070326664433664`，制造真实死锁；期间提交一笔受理请求。

结果：

- 会话 B 收到 `ERROR 1213 Deadlock found`，会话 A 正常提交（MySQL 死锁检测生效）。
- 同期受理请求 29ms 返回 `I`（`orderId=2113516459085926400`），最终 `S/S`，座位/票/hold 各 1，应用未受影响。

## 7. 瓶颈分析与结论

| 验收项（10.4） | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 受理 P99 | ≤50ms（Issue 放宽 ≤100ms） | 16 并发 42.6ms；18 req/s 恒压 12.6ms | 达标；64 并发客户端 P99 700ms（客户端排队） |
| 出票端到端时延 | ≤1s | 无积压时 avg 29.4ms / max 179ms；积压时线性增长 | 无积压达标；积压场景未达标 |
| 单实例消费 | ≥1000 单/秒 | 115~120 单/秒 | 未达标 |
| Redis 预扣 QPS | ≥2 万 | Lua mean 0.94~1.32ms/次，非当前瓶颈 | 未压满，未证伪 |
| 连续压测无泄漏 | 30 分钟 | 10 分钟恒压 18 req/s：0 失败、lag 归零、资源无持续增长 | 部分验证（未跑满 30 分钟） |

瓶颈：

1. **ORDER_CONFIRM 消费单条成本高**：单条事务包含订单查询、座位 CAS、余票扣减、资格更新、outbox 写入，4 并发聚合约 110~128 单/秒；所有订单更新同一 `daily_train_ticket` 行，存在行锁串行化风险（5.4 已证明座位行锁会直接阻塞消费）。
2. **TICKET_CREATE 消费并发为 2**：单线程约 60 单/秒，聚合约 115 单/秒，是出票落库的直接上限。
3. **受理路径非瓶颈**：Lua reserve/confirm 均在 1ms 级，受理服务端 P99 42.6ms，主要成本在 DB 写与事务消息同步发送。

扩容路径（不在 I19 范围，供 I20/后续迭代参考）：按车次/日期拆分余票行或分段扣减、提高消费并发并批量提交、TICKET_CREATE 批量写票，目标 1000 单/秒需约 8~10 个等效消费实例。

## 8. 演练发现与后续动作

| 发现 | 处理 |
| --- | --- |
| 释放幂等标记按 requestId 冲突导致同键重试永久 DUPLICATE | 已修复（releaseKey 加 orderId） |
| business 注解 SQL 下划线列未映射（train_code/ticket_status 为 null） | 已修复（`map-underscore-to-camel-case: true`） |
| member 本地未启用 Nacos 配置时缺 mapper-locations | 已修复（application.yaml 补 `mapper-locations`） |
| Redis 重启后首个请求 17.2s（连接重连） | 记录为恢复期 SLI 劣化，建议预热/健康检查后再放流量 |
| kill -9 产生 2 条 DLQ | 待按 I20 运维手册人工重放；告警已正确触发 |
| 恒压期间约 1 万单在 5 分钟后按 I12 超时关闭（未支付），座位与票正常释放 | 设计行为；关闭后抽查票数为 0、库存差异为 0，证明释放链路在批量场景正确 |
| 单实例出票吞吐不足 1000 | 记录瓶颈与扩容路径，纳入后续容量迭代 |
