## 0. 决策摘要（请先看这一节）

### 0.1 四项能力如何落地

| 能力 | 落地方案 | 核心表 |
|---|---|---|
| 库存与重复购票控制 | 请求幂等键 + Redis Lua 原子预扣（资格/余票/选座）+ 资格表唯一约束 + 异步落库 | `purchase_request`、`purchase_qualification`、`inventory_hold` |
| 异步购票与 Outbox | 受理本地事务 + RocketMQ 事务消息；Cloud Stream 消费组异步出票；重试与死信；消费幂等 | `order_outbox`、RocketMQ |
| 超时关闭与退款释放 | 延迟队列触发；状态条件更新；资格与订单双校验；释放流水幂等；退款两阶段 | `inventory_release_record`、`refund` |
| FIFO 候补补位 | DB 为事实源 + Redis ZSet 为顺序索引；释放后立即匹配；补位订单超时再匹配 | `waitlist_application` |

### 0.2 已拍板的技术路线

| 编号 | 决策 | 结论 | 说明 |
|---|---|---|---|
| D1 | 异步消息与可靠投递 | **Spring Cloud Stream + RocketMQ Binder 事务消息**，`order_outbox` 仅作审计与人工重投 | 复用 Cloud 全家桶：Nacos、Sentinel、Gateway、OpenFeign、Stream Binder |
| D2 | 库存扣减与占座 | **Redis Lua 预扣 + 异步落库 + 定期对账** | Redis 为实时库存事实源，MySQL 为持久账本与查询来源 |

> D2 选 C 带来一个直接收益：同一车次不再需要串行处理，D1 的消费端可以按队列并行扩缩，吞吐由 Redis 分片与消费线程数决定，而不是被一把车次锁卡住。

## 1. 目标与范围

### 1.1 业务目标

1. **不超卖**：任何并发下，已售座位与余票不得为负，不出现同一座位区间重复售卖。
2. **不重单**：同一用户同一乘客同一行程，重复点击/网络重试/消息重投只产生一个有效订单与一个资格。
3. **不丢单**：受理成功后，订单最终一定到达 SUCCESS / EMPTY / FAIL / CLOSED 之一，不会永久停在 INIT/PENDING。
4. **可释放**：取消、超时、退款、改签都能安全归还库存与名额，重复释放不产生副作用。
5. **候补优先**：释放出的名额先给同票档最早候补，候补补位订单超时后继续给下一位。
6. **可运营**：后台能查看排队、Outbox、释放流水、死信，并能人工重放。

### 1.2 技术目标（验收口径，需压测验证）

| 指标 | 目标 |
|---|---|
| 下单受理接口 P99 | ≤ 100 ms（单实例，仅幂等/Lua 预扣/订单 INIT/事务消息半消息） |
| 出票消费吞吐 | 单实例 ≥ 1000 单/秒（每队列 4～8 线程，事务 ≤ 30ms） |
| 出票端到端 P99 | ≤ 1 s（无排队情况下，从受理到 SUCCESS/EMPTY） |
| 数据库事务时长 | P99 ≤ 30 ms，禁止在事务内做 HTTP/Feign/MQ 同步调用 |
| 消息重复消费 | 不产生重复订单、重复扣库存、重复出票 |
| 释放重复执行 | 不产生重复加库存、重复删票 |
| 候补匹配延迟 | 释放后 ≤ 500 ms 触发匹配 |
| 可观测 | 订单状态、消费积压、死信、释放流水、候补队列长度均可查询 |

### 1.3 非目标（本期不做）

- 不对接真实支付通道、真实短信/邮件通道。
- 不引入 Seata/TCC/分布式事务中间件。
- 不重写前端技术栈（继续 Vue 3 + Ant Design Vue + Vue CLI）。
- 不做跨机房、多活、分库分表。
- 不做完整票价浮动、儿童票、学生票、联程票。
- 不改动现有支付/退款/改签的外部接口语义（只做内部增强与兼容）。

### 1.4 约束

- JDK 1.8、Spring Boot 2.6.13、Spring Cloud 2021.0.5、MySQL 8.x、Redis、RocketMQ 已存在。
- `business` 是单体服务内的模块化包结构，本期不拆新微服务。
- 现有 `confirm_order`、`payment`、`refund`、`change_record` 需要平滑演进，不能直接删表重建。
- 会员车票在 `train-member` 库，跨库一致性通过事件与幂等接口实现，不引入分布式事务。

## 2. 设计原则

1. **本地事务优先**：一个业务动作只包一个库的事务；跨服务用“本地事务 + 事件 + 重试 + 幂等”。
2. **资格是库存的唯一凭据**：资格占位（Redis + `purchase_qualification`）成功后才允许占座；释放必须校验资格、座位与订单的对应关系。
3. **幂等键贯穿全链路**：`requestId`、`eventId`、`releaseKey`、`refundKey` 四处唯一约束。
4. **状态机驱动**：所有状态变更使用 `UPDATE ... WHERE id=? AND status=?` 条件更新，禁止无条件覆盖。
5. **先预扣、后落库**：同步接口完成幂等、Lua 预扣、订单 INIT、事务消息；MySQL 落库与出票全部异步。
6. **远程调用移出事务**：Feign 写票/删票改为事件，由消费者重试。
7. **并行优先**：库存正确性由 Lua 原子脚本保证，消费端不要求车次串行，按队列与实例水平扩展。
8. **可回放、可降级**：Outbox 可重放，消费可重投，功能可开关，旧链路可回退。

## 3. 目标架构

### 3.1 总体架构

```text
                    ┌────────────────────────────────────────────┐
                    │  gateway / Sa-Token / 限流（Redis 令牌桶）   │
                    └──────────────────┬─────────────────────────┘
                                       │
                    ┌──────────────────▼─────────────────────────┐
                    │              business 服务                  │
                    │                                            │
  同步受理 ────────►│ PurchaseAcceptService                      │
                    │  ① 请求幂等（Redis + purchase_request）      │
                    │  ② Lua 原子预扣：资格/余票/选座/hold         │
                    │  ③ 订单 INIT + expire_at                   │
                    │  ④ 事务消息 ORDER_CONFIRM                   │
                    │        │                                   │
                    │        ▼                                   │
                    │ RocketMQ（事务消息 + 重试 + 死信）           │
                    │        │                                   │
                    │        ▼                                   │
                    │ TicketConsumer（Cloud Stream 绑定/并发消费） │
                    │  ⑤ 落 inventory_hold + 座位/余票异步落库     │
                    │  ⑥ 订单 SUCCESS + 资格 CONSUMED             │
                    │  ⑦ 事件 TICKET_CREATE                      │
                    │        │                                   │
                    │        ├──► member 内部接口（幂等写票）      │
                    │        ├──► 关闭/超时（Redis ZSet + 兜底）    │
                    │        └──► 候补匹配器（FIFO）               │
                    └────────────────────────────────────────────┘
                                       │
                    ┌──────────────────▼─────────────────────────┐
                    │ Redis：实时库存事实源（Lua 原子操作 + 对账） │
                    │ MySQL：持久账本（hold / 订单 / 流水 / 计数） │
                    └────────────────────────────────────────────┘
```

### 3.2 三条主链路

**A. 新购票**

```text
受理 → Redis Lua 预扣（资格+余票+选座）→ 订单 INIT → 事务消息
     → 消费：hold 落库 → 订单 SUCCESS → 出票事件 → 会员车票
     → 支付 → PAID（移出超时队列）
```

**B. 关闭/退款**

```text
未支付超时/用户取消 → 订单 CLOSED/CANCELLED
                    → 释放资格（校验 qualification + order）
                    → 归还库存 + 释放流水
                    → 触发候补匹配

已支付退款 → 订单 REFUNDING（库存仍预留）
          → 支付通道成功 → 订单 REFUNDED + 释放库存/资格
          → 支付通道失败 → 订单回 PAID，库存不动
```

**C. 候补**

```text
申请 → waitlist_application WAITING + seq_no + ZSet
释放名额 → ZPOPMIN 最早申请 → 事务内扣库存/建待付款订单/资格转移
        → 申请 MATCHED
        → 支付成功 → PAID + 出票
        → 支付超时 → 关闭 + 释放 + 匹配下一位
```

### 3.3 状态机

**订单 `confirm_order.status`**

| 状态 | 编码 | 含义 | 可进入 | 可离开到 |
|---|---|---|---|---|
| 初始 | `I` | 已受理，待出票 | 受理 | P / E / F / C / D |
| 处理中 | `P` | 消费者已认领 | I | S / E / F |
| 成功 | `S` | 已占座/已出票，待支付 | P | Y / C / D |
| 已支付 | `Y` | 支付成功 | S / H | G / X |
| 候补待支付 | `H` | 候补补位成功，待支付 | 补位 | Y / D |
| 退款中 | `G` | 退款已受理，库存仍预留 | Y | R / Y |
| 已退款 | `R` | 退款成功，库存已释放 | G | - |
| 已改签 | `X` | 原订单已改签 | Y | - |
| 已取消 | `C` | 用户主动取消 | I / S | - |
| 已关闭 | `D` | 超时/系统关闭 | I / S / H | - |
| 无票 | `E` | 库存不足 | P | - |
| 失败 | `F` | 出票异常且重试耗尽 | I / P | - |

**资格 `purchase_qualification.status`**

| 状态 | 编码 | 含义 |
|---|---|---|
| 占用 | `H` | 已占位，未消费 |
| 已消费 | `C` | 已绑定成功订单 |
| 已释放 | `R` | 库存已归还 |
| 已转移 | `T` | 转移给候补补位订单 |
| 已过期 | `E` | 受理/占位超时 |
| 已取消 | `X` | 用户取消 |

**候补 `waitlist_application.status`**

`W` 等待中 → `M` 匹配中 → `D` 已匹配（待支付）→ `Y` 已完成；异常分支 `E` 过期、`C` 取消、`F` 失败。

**车票出票状态 `confirm_order.ticket_status`**

`N` 未出票 → `I` 出票中 → `S` 已出票 / `F` 出票失败（由 RocketMQ 重投 + 人工重放修复）。

### 3.4 异步流水线

| 阶段 | 组件 | 并发模型 | 顺序保证 |
|---|---|---|---|
| 受理 | `PurchaseAcceptService` | Web 线程池 + Lua | 同一 requestId 幂等 |
| 消息投递 | RocketMQ 事务消息 | 半消息 + 本地事务回查 | 至少一次；回查兜底 |
| 出票 | `TicketConsumer` | Cloud Stream 绑定，每队列 4～8 线程 | 不要求顺序，幂等键去重 |
| 出票结果 | `TicketIssueConsumer` | 独立消费者组 | 同一 orderId 幂等 |
| 关闭 | `OrderCloseScheduler` | 单实例 + 分布式锁 | 状态 CAS 幂等 |
| 候补 | `WaitlistMatcher` | 按票档分片 | Redis ZSet 分数 FIFO |

## 4. 关键技术方案（已定稿）

### 4.1 D1：Spring Cloud 全家桶消息方案

#### 4.1.1 组件分工

| Cloud 组件 | 在本方案中的职责 | 现状 → 改造 |
|---|---|---|
| Nacos Discovery | 服务注册发现；RocketMQ NameServer 地址外置 | 已用 → 保持 |
| Nacos Config | 消费并发、批量、超时、灰度开关、限流阈值动态调整 | 已引入 → 正式启用 |
| Spring Cloud Gateway | 入口鉴权 + `RequestRateLimiter`（Redis 令牌桶） | 已用 → 增加限流 |
| OpenFeign + LoadBalancer | 会员服务内部调用 | 已用 → 去掉硬编码 `127.0.0.1:8080` |
| Sentinel | 受理热点参数限流、Feign 熔断降级、消费端保护 | 已用 → 规则持久化到 Nacos |
| Spring Cloud Stream + RocketMQ Binder | 事件总线：绑定、消费组、并发、重试、死信 | 新增 `spring-cloud-starter-stream-rocketmq` |
| RocketMQ 事务消息 | 受理本地事务与 `ORDER_CONFIRM` 事件原子提交 | 新增 |
| Seata | **不启用** | `undo_log` 保留，但不接入热路径 |
| Micrometer + Actuator | 受理/消费/积压/对账指标 | 新增 |

#### 4.1.2 事件拓扑

| 事件 | Topic | 生产者 | 消费者组 | 触发 |
|---|---|---|---|---|
| `ORDER_CONFIRM` | `order-confirm` | business 受理（事务消息） | `business-order-confirm` | 预扣成功后出票 |
| `TICKET_CREATE` | `ticket-create` | business 出票成功 | `member-ticket-create` | 写会员车票 |
| `ORDER_CLOSE` | `order-close` | 关闭调度 / 用户取消 | `business-order-close` | 关单并释放 |
| `INVENTORY_RELEASED` | `inventory-released` | 关闭 / 退款 / 改签 | `business-waitlist-match` | 触发候补补位 |

- 消费失败：`push.maxReconsumeTimes=5`，超过进入 `%DLQ%{consumerGroup}`。
- 死信处理：后台按 `order_outbox` 与 DLQ 双视图人工重放。
- 超时关闭不走 RocketMQ 延迟等级（4.9 只有 18 档，无法精确到 5 分钟），仍用 Redis ZSet + Quartz 兜底（见 4.3）。

#### 4.1.3 事务消息怎么用

```text
accept(req):
  1. Redis Lua 预扣成功，拿到 holdToken
  2. rocketMQTemplate.sendMessageInTransaction(
       topic=order-confirm,
       message={orderId, requestId, holdToken},
       arg=受理上下文)
       ├─ 半消息发送成功
       ├─ executeLocalTransaction:
       │    TransactionTemplate 写 purchase_request /
       │    purchase_qualification / confirm_order(I) / order_outbox
       │    成功 → COMMIT；异常 → ROLLBACK
       └─ 半消息发送失败 → Lua release(holdToken)
  3. 返回 orderId
```

- `checkLocalTransaction`：按 `requestId` 查 `purchase_request`，存在即 COMMIT，不存在即 ROLLBACK。
- `order_outbox` 与业务同事务写入，但**不承担主投递**：用于审计、对账和人工重投，避免“事务消息回查失败”时无据可查。
- 事务消息解决“落库成功、发消息失败”；消费幂等解决“至少一次”带来的重复。

#### 4.1.4 消费端可靠性

| 能力 | 实现 |
|---|---|
| 消费幂等 | `confirm_order.status='I' → 'P'` 条件更新；`inventory_hold` 唯一键 `(hold_token, seat_id)` |
| 重试 | Binder `maxReconsumeTimes=5`，退避由 RocketMQ 负责 |
| 死信 | `%DLQ%business-order-confirm` + 后台重放 |
| 消费中断 | 消息未 ACK 自动重新投递，不依赖 PENDING 表 |
| 顺序 | 不要求全局/车次顺序；库存正确性由 Redis Lua 与幂等键保证，因此可以高并发消费 |
| 积压 | 消费并发与队列数通过 Nacos 动态调整 |

#### 4.1.5 为什么不用纯 Outbox Relay

| 维度 | 事务消息（选用） | 纯 Outbox Relay |
|---|---|---|
| 投递延迟 | 半消息已在 Broker，本地提交后立即可见 | 依赖轮询，默认 50ms 起 |
| 实现成本 | 一个 `TransactionListener` | Relay 线程、`SKIP LOCKED`、退避、归档 |
| 可靠性 | 半消息 + 回查，原生保证 | 需自行保证不丢不重 |
| 参考图一致性 | Outbox 仍保留为审计表 | 完全一致 |

> 备选保留：若后续 Broker 不可用，可把 `OrderEventPublisher` 切回 Outbox Relay + Redis Stream，业务代码不变（接口已抽象）。

### 4.2 D2：库存与占座

#### 4.2.1 职责边界

| 层 | 角色 | 说明 |
|---|---|---|
| Redis | 实时事实源 | 资格占位、余票、座位区间占用、hold 凭据 |
| MySQL | 持久账本 | `inventory_hold`、订单、资格、释放流水、余票计数快照 |
| 对账任务 | 收敛器 | 启动预热 + 每分钟比对，修正 Redis 与 MySQL 偏差 |

#### 4.2.2 Redis Key 设计

| Key | 类型 | 含义 | TTL |
|---|---|---|---|
| `purchase:req:{requestId}` | hash | 幂等状态 `state / orderId / holdToken` | 24h |
| `qual:{date}:{trainCode}:{passengerId}` | string | 购票资格，值为 `orderId` | 支付窗口 + 缓冲 |
| `inv:t:{date}:{trainCode}:{startIdx}:{endIdx}` | hash | 各席别余票 `ydz / edz / rw / yw` | 随车次数据 |
| `inv:seat:{date}:{trainCode}:{seatId}` | hash | 已占区间：field=`seg:{idx}`，value=`orderId` | 随车次数据 |
| `inv:pool:{date}:{trainCode}:{seatType}:{startIdx}:{endIdx}` | list | 候选座位池（懒清理） | 随车次数据 |
| `hold:{holdToken}` | hash | 预扣凭据：订单、座位、区间、乘客 | 5 分钟 |
| `rel:{releaseKey}` | string | 释放幂等标记 | 24h |
| `waitlist:match:key:{key}` | string | 按票档的匹配合并锁，拿到的实例负责跑完整轮 | 2s |
| `waitlist:retry:{key}` | zset | 匹配失败退避队列，`score=可重试时间`，`member=applicationId` | 1h |
| `waitlist:fail:{applicationId}` | string | 连续匹配失败次数 | 10min |
| `wl:evt:{eventId}` | string | 候补匹配事件幂等标记 | 10min |

- 座位占用用 hash field 记录 `orderId`，释放时按 `HGET == orderId` 比较后再 `HDEL`，从根上避免“旧订单释放新订单名额”。
- 候选池允许存在已占座位的脏项：Lua 弹出后校验，占用则丢弃，释放时再回填。

#### 4.2.3 Lua 脚本职责

**`reserve.lua`（预扣，一次往返完成）**

```text
1. EXISTS purchase:req:{requestId} → 返回 DUPLICATE（携带已有 orderId）
2. 对每个乘客：SET qual:{date}:{trainCode}:{pid} {orderId} NX PX ttl
   - 任一失败 → 回滚已写资格 → 返回 DUPLICATE
3. HGET inv:t 对应席别余票，< n → 回滚资格 → 返回 NO_TICKET
4. 从候选池弹出座位，按 [startIdx, endIdx) 逐段 HEXISTS 校验
   - 选中 n 个 → HSET inv:seat seg:{i} = orderId
   - 候选耗尽 → 回滚已占座位/资格 → 返回 NO_TICKET
5. HINCRBY inv:t 余票 -n
6. HSET hold:{holdToken} + PEXPIRE 5 分钟
7. HSET purchase:req state=RESERVED, orderId, holdToken
```

- 整个脚本单次 RTT、原子执行，不存在“扣了余票没占座”的中间态。
- 单次候选上限 64，避免 Lua 长时间阻塞 Redis。

**`release.lua`（释放，幂等）**

```text
1. EXISTS rel:{releaseKey} → 返回 ALREADY
2. 对每个乘客：GET qual == orderId ? DEL : 跳过
3. 对每个座位每段：HGET inv:seat == orderId ? HDEL + 回填候选池 : 跳过
4. HINCRBY inv:t 余票 +n
5. SET rel:{releaseKey} 1 EX 86400
```

- 资格、座位的比较删除都以 `orderId` 为凭据，重复执行不会多还库存。

**`confirm.lua`（落库成功后收尾）**

```text
1. HDEL hold:{holdToken}（仅当 hold.orderId == 当前订单）
2. 续期 qual 到支付窗口
```

#### 4.2.4 异步落库

| 步骤 | 写 MySQL | 幂等保证 |
|---|---|---|
| 1 | `insert inventory_hold(hold_token, seat_id, ...)` | 唯一键 `(hold_token, seat_id)` |
| 2 | `update daily_train_seat set sell=?, version=version+1 where id=? and version=?` | 版本 CAS，失败重读 Redis 位图后重试 3 次 |
| 3 | `update daily_train_ticket set ydz=ydz-n ...` | 派生值，允许滞后；由对账按 `inventory_hold` 聚合校正 |
| 4 | `update confirm_order set status='S' ...` | 状态 CAS |
| 5 | `update purchase_qualification set status='C' ...` | 条件更新 |

- 落库失败不回滚 Redis：消费重试继续落库，超过 5 次进死信并 `release.lua` 回补。
- MySQL 计数不是判库存的依据，只服务查询与后台展示；真实可用量以 Redis 为准。

#### 4.2.5 一致性与故障处理

| 场景 | 处理 |
|---|---|
| Redis 预扣成功、事务消息发送失败 | 同步 `release.lua` 回补 |
| 本地事务失败 | 事务消息 ROLLBACK + `release.lua` 回补 |
| 消费失败/超时 | hold TTL 到期自动消失；关单任务按 `expire_at` 关闭并 `release.lua` |
| Redis 重启丢数据 | AOF `everysec`；重启回放期间受理快速失败；启动后按 MySQL `inventory_hold` 重建 |
| Redis 不可用 | 受理直接返回 `SYSTEM_BUSY`（可重试），**禁止绕过 Redis 直写 MySQL** |
| 对账差异 | 每分钟比对，差异写对账日志并告警；以 `inventory_hold` 聚合值为准回填 |

**Redis 部署要求（不满足则不启用预扣）**

- 开启 AOF `appendfsync everysec`，`maxmemory-policy noeviction`（禁止淘汰库存 key），显式设置 `maxmemory` 并监控。
- **本期部署形态：单机 AOF**（演示/单实例）。Redis 宕机期间受理返回 `SYSTEM_BUSY`，恢复后先对账再放量；key 设计不依赖副本语义。
- 后续上生产可平滑升级为主从 + Sentinel（补充 `min-replicas-to-write 1`）或 Cluster，业务代码与 key 结构不变。
- 库存 key 与业务缓存使用不同逻辑库或前缀，避免被缓存淘汰策略误伤。

#### 4.2.6 与另一条路线的关系

- 原“MySQL 行锁 + 原子条件更新”不废弃：它是**对账与修复**的依据。`inventory_hold` 聚合出的座位占用可直接修正 `daily_train_seat.sell`。
- Redisson 仅保留令牌、短防重、定时任务互斥，不再承担车次级订单锁。
- 若 Redis 预扣压测不达标，可退回“MySQL 行锁”实现；库存服务接口不变，切换成本集中在 `InventoryService` 实现类。

### 4.3 超时关闭触发方式

| 方案 | 精度 | 实现 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|---|
| Redis ZSet 延迟队列 | 秒级 | `ZADD order:close score=expireAt member=orderId`，扫描 `ZRANGEBYSCORE` + `ZREM` | 轻量、精确、与预扣同栈 | 需要扫描线程与分布式锁 | **推荐** |
| RocketMQ 延迟消息 | 固定等级 | 发送延迟消息 | 成熟 | 依赖 Broker，等级有限 | 备选 |
| Quartz 扫表 | 分钟级 | `where status in (...) and expire_at < now()` | 简单 | 延迟大、扫表压力 | 兜底/对账 |

**推荐组合**：Redis ZSet 主触发 + Quartz 每 5 分钟兜底扫表，防止 ZSet 丢数据。

### 4.4 FIFO 候补

**事实源与索引分离**

- **DB `waitlist_application` 是事实源**：状态、资格、匹配结果都在 DB。
- **Redis ZSet 是顺序索引**：`waitlist:{date}:{trainCode}:{start}:{end}:{seatType}`，`score = seq_no`，`member = applicationId`。
- `seq_no` 由 Redis `INCR waitlist:seq:{key}` 生成；Redis 丢失时用 DB `max(seq_no)+1` 恢复。

**为什么不用纯 DB 轮询**

- 纯 DB `order by seq_no limit 1 for update skip locked` 也能实现 FIFO，但释放瞬间的匹配延迟取决于轮询间隔。
- ZSet 在释放时立即 `ZPOPMIN`，匹配延迟可做到毫秒级；DB 仍负责最终校验与事务。

**FIFO 保证**

1. 申请时一次性分配 `seq_no`，之后不改变。
2. 匹配失败按原因分流：
   - `NO_STOCK` / `SEAT_CONFLICT`：用**原分数**重新 `ZADD`，不重新排队，并结束本轮（不再空转队列）。
   - 同一申请连续失败 ≥ 3 次：计数置入 `waitlist:fail:{applicationId}`，转入 `waitlist:retry:{key}`（`score=now+30s`），`seq_no` 不变，到点由重试推进器放回主队列。
3. 同一票档的多个释放事件按 key 合并：只有拿到 `waitlist:match:key:{key}` 的实例执行一轮匹配，其余事件直接 ACK，避免同一申请被连续撞多次。
4. 事件幂等：`wl:evt:{eventId}` 首次才处理，挡住 MQ 重投。
5. 取消后重新申请，生成**新记录、新 seq_no**，排到队尾（符合参考图要求）。
6. 同一乘客同一票档只允许一条 active 申请，`active_key` 唯一约束兜底。

### 5.4 迁移与兼容

1. **只增不删**：新增列全部可空，新增表不影响旧代码；旧订单 `request_id` 为空，不回填也能运行。
2. **存量订单只读兼容**：`request_id` 为空的旧订单走“旧释放逻辑”：按 `order_id` 无法反查时，回退到 `member + date + train + start + end + 最近创建`，并记录告警；新订单必须走新逻辑。
3. **会员车票回填**：为存量 `ticket` 补 `order_id` 需要一次性脚本，按 `member + date + train + start + end + seat` 匹配 `confirm_order.tickets`；匹配不上的保留 `NULL`，旧退票逻辑仍可工作。
4. **灰度开关**（Nacos 配置，运行时生效）：
   - `feature.purchase.v2.enabled`
   - `feature.inventory.redis-first.enabled`（关闭则退回 MySQL 行锁实现）
   - `feature.timeout-close.enabled`
   - `feature.waitlist.enabled`
5. **回滚**：关闭开关即回到旧链路；新增表保留，不影响旧逻辑；Outbox 中未投递事件在回滚前需排空或标记。

### 6.3 切换策略（D4：直接替换）

1. 新受理接口 `POST /business/web/purchase/apply` 上线，旧 `POST /business/web/confirm-order/do-storage` 返回 `410 Gone`，保留一个版本周期后删除路由。
2. `Idempotency-Key` 改为必填；由前端在下单页生成 UUID，服务端校验格式并写入 `purchase_request.idempotency_key`。

5. 支付/退款/改签路径与请求体保持不变；退款内部改为两阶段，对外仍同步返回受理结果。
6. 旧订单状态映射：`S` 显示“待支付”，`Y` 显示“已支付”，`D` 显示“已关闭”，`H` 显示“候补待支付”。

## 7. 核心流程设计

### 7.1 受理（同步、快速）

```text
PurchaseAcceptService.accept(req, memberId, idempotencyKey)

1. 网关限流 + Sentinel 热点参数限流（trainCode）
2. 校验参数、乘客归属、车次与席别合法性
3. 幂等快速判断：purchase:req:{requestId} 已存在 → 返回已有 orderId/状态
4. Lua reserve：
   - 资格 SETNX（同一乘客同一车次只能有一个有效占位）
   - 余票判断 + 座位区间占用 + 生成 holdToken
   - 失败：DUPLICATE / NO_TICKET，直接返回
5. 事务消息 ORDER_CONFIRM：
   - 半消息发送
   - executeLocalTransaction → TransactionTemplate：
     a. insert purchase_request（uk_request_id）
     b. insert purchase_qualification（uk_active）
     c. insert confirm_order(status=I, expire_at=now+5m)
     d. insert order_outbox（审计）
   - 成功 COMMIT；异常 ROLLBACK
6. 半消息发送失败或回滚 → Lua release(holdToken)
7. 返回 {requestId, orderId, status=I}
```

**关键点**

- 预扣在事务消息之前：保证消息一旦提交，库存一定已经预占。
- 任何一步失败都走 `release.lua`，重试也由它幂等兜底。
- 资格 `active_key` 唯一约束是“重复购票”的最终防线，Redis 只做快速拦截。
- 令牌（SK Token）继续作为入口削峰，不作为正确性依据。

### 7.2 消费出票（异步、幂等）

```text
TicketConsumer.onMessage(msg)

1. 订单状态 CAS：
   update confirm_order set status='P' where id=? and status='I' and expire_at>now()
   -- 0 行：已处理/已关闭/已过期 → ACK 跳过
2. 读取 hold:{holdToken}
   - 不存在：查 inventory_hold 是否已落库
     - 已落库 → ACK（重复消息）
     - 未落库 → 订单 FAIL + ACK（hold 已过期，由关单任务释放）
3. TransactionTemplate（一条消息一个事务）：
   a. insert inventory_hold（uk_hold_seat 幂等）
   b. 座位落库：update daily_train_seat set sell=?, version=version+1
        where id=? and version=?；失败重读 Redis 位图后重试 3 次
   c. 余票落库：update daily_train_ticket set ydz=ydz-n ...（派生值，允许滞后）
   d. 资格置 C：update purchase_qualification set status='C' where order_id=?
   e. 订单：status='S', ticket_status='I', expire_at=now+5m
   f. insert order_outbox(TICKET_CREATE)
4. Lua confirm：删除 hold、资格续期到支付窗口
5. 发送 TICKET_CREATE 事件
6. ACK
7. 异常：不 ACK，RocketMQ 重投；超过 5 次 → DLQ + 订单 FAIL + Lua release（失败回滚不发候补匹配事件，见 7.8）。
```

**一致性要点**

- 库存正确性不依赖 MySQL 行锁或车次串行锁，完全由 Lua 原子预扣保证。
- `inventory_hold` 唯一键 + 订单状态 CAS 是消费幂等的双保险。
- 座位 `sell` 落库失败不影响用户下单结果，由对账任务按 Redis 位图修正。
- 出票（写会员车票）不在本事务，由 `TICKET_CREATE` 异步完成。

### 7.3 出票事件（跨服务最终一致）

```text
TicketIssueConsumer（订阅 ticket-create）:
  1. 查 order，status=S，ticket_status=I
  2. 调 member /internal/feign/ticket/issue（带 orderId + passengerId）
     - member 侧 uk(order_id, passenger_id) 幂等
  3. 成功：order.ticket_status=S；order_outbox 审计记录标记 SENT
  4. 失败：RocketMQ 重投（最多 5 次），超过阈值 → ticket_status=F + 告警 + 死信
```

- 订单在 `ticket_status=I` 时对用户显示“出票中”，避免“已成功但没票”的误解。
- 会员服务不可用时，订单仍可支付吗？建议：**未出票不允许支付**，支付接口校验 `ticket_status=S`。

### 7.4 取消与超时关闭

```text
OrderCloseService.close(orderId, reason)

1. TransactionTemplate（先落账，保证可恢复）:
   a. update confirm_order
        set status='D' or 'C', close_reason=?, version=version+1
      where id=? and status in ('I','S','H')
      -- 0 行 → 已处理，直接返回
   b. update purchase_qualification
        set status='R', active_key=null
      where order_id=? and status in ('H','C')
   c. update inventory_hold set status='R', release_time=now(3)
      where order_id=? and status='H'
   d. insert inventory_release_record(
        idempotent_key='REL:{orderId}:{reason}')
      -- 唯一键冲突 → 已释放，跳过
   e. insert order_outbox(WAITLIST_MATCH, payload={票档key})
   f. insert order_outbox(TICKET_DELETE, orderId)  -- 若已出票
   commit
2. commit 后立即 Lua release（幂等）：
   - 资格：GET qual == orderId ? DEL
   - 座位：HGET inv:seat == orderId ? HDEL + 回填候选池
   - 余票：HINCRBY +n
   - rel:{releaseKey} 已存在 → 跳过
3. Lua 释放失败 → 进入重试队列；hold TTL 到期兜底，对账任务修正
4. ZREM order:close orderId
5. 发送 INVENTORY_RELEASED 事件（触发候补）
```

**为什么先 DB 后 Redis**

- 先落账再释放，最坏情况是“名额晚归还几秒”，不会出现“库存已放出、订单仍有效”的超卖窗口。
- 反向顺序（先 Redis 后 DB）在 DB 提交失败时会制造双重占用，必须靠对账兜底，风险更高。

**触发方式**

- 用户取消：`POST /business/web/order/{orderId}/cancel`。
- 超时：`OrderCloseScheduler` 从 `order:close` ZSet 取到期订单，调用 `close(orderId, "TIMEOUT")`。
- 兜底：Quartz 每 5 分钟扫 `confirm_order where status in ('I','S','H') and expire_at < now()`。
- 支付成功：`ZREM order:close orderId`。

**参考图要求的“旧订单重试不释放新名额”**

- DB 侧：`update purchase_qualification ... where order_id=? and status in ('H','C')`，0 行即跳过。
- Redis 侧：`GET qual == orderId` 与 `HGET inv:seat == orderId` 才删除；旧订单的 orderId 与新订单不同，比较失败即跳过。
- 再加 `inventory_release_record` 唯一键与 `rel:{releaseKey}`，三重幂等。

### 7.5 退款（两阶段）

```text
RefundService.apply(orderId, reason, idempotencyKey)

1. TransactionTemplate:
   a. update confirm_order set status='G'
      where id=? and status='Y'
      -- 0 行 → 状态不允许
   b. insert refund(status='REFUNDING', idempotent_key='REFUND:{orderId}')
      -- 唯一键冲突 → 返回已有退款
   -- 注意：此时不释放库存，资格保持 C
2. 调用支付通道（演示：直接成功）
3a. 成功 TransactionTemplate:
     - update order set status='R' where id=? and status='G'
     - 释放资格/库存（同 7.4：DB 落账 + Lua release，release_type='R'）
     - update refund set status='SUCCESS'
     - outbox TICKET_DELETE + WAITLIST_MATCH
3b. 失败 TransactionTemplate:
     - update order set status='Y' where id=? and status='G'
     - update refund set status='FAILED', fail_reason=?
     -- 库存不动，资格仍为 C
```

**为什么两阶段**

- 支付通道失败时，库存已释放会造成“已退款但没退钱”的超卖窗口。
- 受理后保持预留，成功才释放，符合参考图“退款受理后预留名额，成功后才释放”。

### 7.6 候补申请

```text
WaitlistService.apply(req, memberId)

1. 校验车次、区间、席别、乘客归属
2. TransactionTemplate:
   a. insert waitlist_application(
        status='W',
        seq_no=INCR waitlist:seq:{key},
        active_key=businessKey,
        request_id=idempotencyKey)
      -- uk_active 冲突 → 已存在候补，返回已有记录
3. ZADD waitlist:{key} score=seq_no member=applicationId
4. ZINCRBY waitlist:count:{key} 1
5. 返回 {applicationId, seqNo, status=W}
```

- `active_key` 与购票资格使用相同业务键格式，避免“已有票又候补”或“重复候补”。
- 候补申请不扣库存、不建订单。

### 7.7 补位匹配

```text
WaitlistMatcher.onRelease(event)

1. 事件幂等：SETNX wl:evt:{eventId} 1 EX 600
   -- 已存在 → ACK（MQ 重投不重复触发）
2. 按票档合并：SETNX waitlist:match:key:{key} 1 PX 2000
   -- 拿不到 → 已有实例在本轮处理该票档，直接 ACK（事件被吸收）
3. 循环匹配（直到预扣失败或队列为空）：
   a. applicationId = ZPOPMIN waitlist:{key}
      -- 为空 → 结束
   b. Lua reserve 预扣（事务外，同 7.1：资格/余票/选座）
      - NO_STOCK / SEAT_CONFLICT：
          INCR waitlist:fail:{applicationId} + EXPIRE 10min
          计数 < 3 → 原 score ZADD 回主队列，结束本轮
          计数 ≥ 3 → ZADD waitlist:retry:{key} score=now+30s，DEL 计数，结束本轮
      - 预扣成功 → 进入 3c
   c. TransactionTemplate:
      a) select application for update
         - status != 'W' → Lua release，丢弃，继续下一个
      b) hold 落库（同 7.2）
      c) 创建订单：status='H'，expire_at=now+5m，request_id='WL:{applicationId}'
      d) 资格转移：
           DB：update purchase_qualification
                 set order_id=#{newOrderId}, status='C'
               where id=#{applicationQualificationId} and status='H'
           Redis：SET qual:{date}:{trainCode}:{passengerId} {newOrderId}
      e) update waitlist_application
           set status='D', matched_order_id=?, expire_at=now+5m
      f) insert order_outbox(WAITLIST_NOTIFY, applicationId)
      commit
   d. ZADD order:close score=expireAt member=newOrderId
   e. DEL waitlist:fail:{applicationId}
   f. 继续下一位（下一轮 reserve 失败即自然结束）
4. finally：DEL waitlist:match:key:{key}
```

- **退避重试推进**：`WaitlistRetryPromoter` 每秒扫描 `ZRANGEBYSCORE waitlist:retry:{key} 0 now`，按 DB `seq_no` 放回主队列并 `ZREM`，保证退避后仍按原顺序排队。
- **锁必须带 TTL**：`waitlist:match:key` 2 秒、`wl:evt` 10 分钟，实例崩溃不会卡死票档或申请。
- **不再按事件里的 `releasedSeats` 计数**：以 `reserve.lua` 的实际结果为准，避免“事件说有座、实际无座”时空转。
- **候补优先于新购票**：受理新购票前查 `waitlist:count:{key}`；若 > 0 且当前无票，返回 `WAITLIST_PRIORITY`，引导候补。
- **补位订单超时**：走 7.4 关闭，释放后再次触发 `WAITLIST_MATCH`，匹配下一位。
- **补位订单退款**：走 7.5 退款，释放后再次匹配。
- **取消后重新申请**：取消置 `CANCELLED`、`active_key=NULL`、`ZREM`；重新申请生成新 `id/seq_no`，排到队尾。

### 7.8 释放与候补的协作

```text
真实释放（取消 / 超时 / 退款成功 / 改签 / 补位订单超时）
  → DB 事务写 release_record + outbox(WAITLIST_MATCH, key)
  → 提交后 Lua release 归还 Redis 名额
  → INVENTORY_RELEASED 触发 WaitlistMatcher

失败回滚（受理失败 / 落库失败 / 消费死信）
  → 只做 Lua release + 写库存差异标记
  → **不发 WAITLIST_MATCH**，避免“释放→匹配→再失败→再释放”的自激循环
  → 由对账任务修正后，随下一次真实释放或定时匹配消化
```

- 匹配失败不影响释放结果；匹配器可重试，但同一申请 30 秒内最多尝试 3 次。
- 同一票档的多个释放事件由 `waitlist:match:key` 合并成一轮匹配，其余事件直接 ACK。
- 只有 `release.lua` 实际归还了容量（`rel:{releaseKey}` 首次且删除成功）才发事件；重复释放不发。

## 8. 性能与容量设计

### 8.1 性能目标与瓶颈

| 环节 | 主要开销 | 优化手段 |
|---|---|---|
| 受理 | 1 次 Lua + 3～N 次 INSERT + 半消息 | Lua 单 RTT、单事务、无 Feign、雪花 ID |
| 消息投递 | 事务消息半消息 + 回查 | Broker 异步；回查只按 `requestId` 查主键 |
| 消费 | 读 hold + `inventory_hold` 落库 + 状态更新 | 队列并行、一条消息一个短事务、幂等键 |
| 出票 | Feign 写会员车票 | 事件异步、幂等接口、批量/重试 |
| 关闭 | ZSet 扫描 + 状态 CAS + Lua 释放 | 批量 200、秒级扫描、Quartz 兜底 |
| 候补 | ZSet 操作 + Lua + 事务 | 按票档分片、匹配锁、原分数回队 |

### 8.2 热点分析

1. **热点 O-D 余票 key**：同一车次同一区间的 `inv:t` 被所有请求访问。缓解：
   - Lua 单 RTT，避免多次往返；
   - 按 `date + trainCode` 做 Redis Cluster slot 亲和，避免跨 slot；
   - 单 key 热点超过 2 万 QPS 时按席别拆 key；
   - 监控 Lua 执行耗时，超过 5ms 告警。
2. **热点座位 key**：同一座位被并发争抢。缓解：
   - 候选池按区间拆分，减少无效扫描；
   - Lua 内校验后占用，失败即换下一个；
   - 候选上限 64，避免长时间阻塞。
3. **MySQL 落库**：`inventory_hold` 高频插入。缓解：
   - `uk_hold_seat` 保证幂等，重复消息直接忽略；
   - 按 `(date, train_code)` 归档历史数据；
   - 座位 `sell` 更新使用版本 CAS，失败重读 Redis 后重试。

### 8.3 并发与容量参数（初始建议）

| 参数 | 初始值 | 调整依据 |
|---|---|---|
| RocketMQ Topic 队列数 | 8 | 消费吞吐与顺序无关，可水平扩容 |
| 单队列消费线程 | 4～8 | CPU、DB 连接池 |
| 消费组实例数 | 2～4 | 队列数与故障冗余 |
| Lettuce 连接池 | 32～64 | Lua QPS |
| Redis 单实例 Lua QPS 目标 | ≥ 2 万 | 预扣脚本 10～20 个操作 |
| Hikari 最大连接 | 20～30/实例 | DB 承载 |
| 座位 CAS 重试 | 3 | 冲突率 |
| 死锁重试 | 2 | 死锁率 |
| 对账批量 | 500 车次/轮 | 对账耗时 |

### 8.4 事务最小化

**禁止在事务内做的事**

- Feign/HTTP 调用
- MQ 同步发送
- 大量日志/JSON 序列化
- 循环查库（N+1）
- 等待锁超过 100ms

**推荐做法**

- 事务外准备数据（车次、车厢、候选座位、票价）；
- 事务内只做条件更新与状态推进；
- 远程调用通过事务消息/事件异步化；
- 批量插入使用 MyBatis `foreach`，但单批不超过 200 条。

| `select ... from purchase_request where request_id=?` | `uk_request_id` |

### 8.6 压测方案

| 场景 | 方法 | 观察指标 |
|---|---|---|

工具：JMeter 或 Gatling；数据准备用 SQL 批量插入；监控用 MySQL `performance_schema`、Redis `INFO`、应用 Micrometer（需新增）。

### M2：异步出票与事务消息

**交付物**

- `spring-cloud-starter-stream-rocketmq` 接入，`ORDER_CONFIRM` 生产者/消费者绑定。
- `TransactionListener`：本地事务 + 回查。
- `TicketConsumer`：状态 CAS、`inventory_hold` 落库、座位/余票异步落库、订单 SUCCESS。
- `TicketIssueConsumer`：会员车票幂等写入。
- 消费幂等、重试、死信与后台重放入口。
- vue-ui 下单页切换到 `/purchase/apply`，生成 `Idempotency-Key`，接入新错误码与 410 提示。
- 对账任务：Redis 与 MySQL 库存比对与修正。

**验收**

- 消息重复投递不重复扣库存/出票。
- 消费者中断后消息自动重投，订单最终完成。
- 死信可观测、可重放。
- 出票端到端 P99 ≤ 1s（无排队）。
- 失败回滚只释放库存，不触发候补匹配事件。

### M3：关闭、取消与退款释放

**交付物**

- 用户取消接口。
- Redis ZSet 超时队列 + Quartz 兜底。
- 统一释放服务：DB 落账 + `release.lua` + 释放流水 + 三重幂等。
- 退款两阶段：REFUNDING → REFUNDED / 回滚 PAID。
- 会员车票按 `order_id` 删除。
- 后台释放流水与卡单页面。

**验收**

- 未支付订单超时后库存归还、资格释放、记录流水。
- 重复取消/重复退款不重复加库存。
- 旧订单重试不释放新订单名额。
- 退款失败时库存与订单状态可回滚。

### M4：FIFO 候补补位

**交付物**

- 候补申请/取消/我的候补接口。
- Redis ZSet 队列 + `seq_no`。
- 事件合并锁 `waitlist:match:key`、事件幂等 `wl:evt`、失败退避 `waitlist:retry` + `WaitlistRetryPromoter`。
- 释放后匹配器：Lua 预扣、建待付款订单、资格转移。
- 失败回滚不发匹配事件，只写差异标记等待对账。
- 补位订单超时/退款后再匹配。
- 候补优先于新购票的拦截。
- 会员端“候补”入口与我的候补列表；后台候补管理页。

**验收**

- 同票档严格按提交顺序匹配。
- 取消后重新申请排到队尾。
- 补位订单超时后下一位获得名额。
- 退款释放后候补优先于新购票。
- 匹配延迟 ≤ 500ms。

### M5：压测、可观测与灰度

- 指标、日志、告警看板。
- 灰度方案与回滚演练。

**验收**

### 10.2 一致性断言

每次场景结束后执行：

```sql
-- 1. 余票不得为负
select count(*) from daily_train_ticket where ydz < 0 or edz < 0 or rw < 0 or yw < 0;

-- 2. 成功/已支付订单数不得超过对应 O-D 席别库存初始值
-- （按日期+车次+区间+席别聚合，与初始库存对比）

-- 3. 同一乘客同车次不得有两个有效资格
select active_key, count(*) from purchase_qualification
 where active_key is not null
 group by active_key having count(*) > 1;

-- 4. 释放流水不得重复
select idempotent_key, count(*) from inventory_release_record
 group by idempotent_key having count(*) > 1;

-- 5. 已支付订单必须有且仅有一条支付记录
select order_id, count(*) from payment
 group by order_id having count(*) > 1;

-- 6. 已退款订单必须有且仅有一条成功退款记录
select order_id, count(*) from refund
 where refund_status='SUCCESS' group by order_id having count(*) > 1;

-- 7. 会员车票不得重复
select order_id, passenger_id, count(*) from ticket
 where order_id is not null
 group by order_id, passenger_id having count(*) > 1;
```

### 10.3 故障注入

| 故障 | 预期 |
|---|---|
| 消费者 kill -9 | 消息自动重投，订单最终完成，不重复扣库存 |
| Redis 重启 | AOF 回放期间受理快速失败；hold 丢失由对账按 MySQL 重建；令牌可降级 |
| Redis 宕机（单机） | 受理返回 `SYSTEM_BUSY`；恢复后先对账再放量 |
| RocketMQ Broker 重启 | 半消息回查恢复，不丢单；消费重投 |
| MySQL 死锁 | 自动重试 2 次，超过则订单 FAIL 并 Lua release |
| 会员服务超时 | 出票事件重试，订单 ticket_status=I/F，用户可见 |
| 支付通道超时 | 退款保持 REFUNDING，可查询/重试，不提前释放 |
| 时钟回拨 | 超时判断以 DB/Redis 服务端时间为准，增加容差 |

### 10.4 性能验收

- 受理 P99 ≤ 50ms（Lua + 本地事务 + 半消息）；
- 出票端到端 P99 ≤ 1s（无排队）；
- 单实例消费 ≥ 1000 单/秒（多实例水平扩展）；
- Redis 预扣 ≥ 2 万 QPS/实例（单 key 热点除外）；
- 超时关闭延迟 ≤ 2s（ZSet 扫描周期）；
- 候补匹配延迟 ≤ 500ms；
- 连续压测 30 分钟无内存泄漏、无连接池耗尽、无消费积压。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Redis 库存 key 内存增长 | OOM / key 被淘汰 | AOF、`noeviction`、按车次设置 TTL、监控内存；禁止 LRU 淘汰库存 key |
| Redis 单点故障 | 预扣不可用 | 本期单机 AOF；不可用时受理快速失败，恢复后对账；生产再升级主从 + Sentinel |
| 预扣与落库不一致 | 库存偏差 | 每分钟对账 + 告警 + 按 `inventory_hold` 聚合回填 |
| MySQL 热点行 | 落库吞吐上不去 | 短事务、按车次归档、批量更新；实时扣减由 Redis 承担 |
| 死锁 | 订单失败率上升 | 固定更新顺序、CAS、重试、监控死锁日志 |
| 存量数据迁移 | 旧订单无法释放 | 旧逻辑兜底 + 回填脚本 + 告警 |
| 状态兼容 | 前端显示异常 | 状态映射表 + 灰度 + 回归测试 |
| 出票最终一致 | 用户看到“成功但没票” | `ticket_status` + 前端“出票中” + 告警 |
| 候补公平性 | 用户投诉 | `seq_no` 不可变、原分数回队、审计日志 |
| 过度设计 | 交付变慢 | 开关 + 分阶段 + 先正确后性能 |
| 团队不熟悉 Cloud Stream / 事务消息 | 运维风险 | M0 预研 + 运维手册 + 监控 + 演练 |
